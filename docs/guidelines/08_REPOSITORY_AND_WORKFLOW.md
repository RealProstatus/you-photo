## 1. Управление конфигурацией репозитория (п. 3.1 «Структуры проекта»)

1. **Единая система контроля версий**:
   - Используется **Git** с центральным репозиторием на **GitHub**.
2. **Фиксация зависимостей**:
   - Все пакеты Python строго фиксируются с указанием версий в файлах [requirements.txt](../../requirements.txt), [requirements-desktop.txt](../../requirements-desktop.txt) и [pyproject.toml](../../pyproject.toml).
   - Обновление сторонних пакетов (`Django`, `PySide6`, `PostgreSQL`, `MinIO`, `Apprise`) проводится только после прогона автотестов (`п. 4 Функциональной спецификации`).
3. **Декларативное окружение и хранение секретов (`152-ФЗ`, `S-SEC-01`, `S-SEC-02`)**:
   - Конфигурация серверного окружения описывается декларативно через `deploy/Dockerfile.backend`, `deploy/docker-compose.yml` и `deploy/nginx/nginx.conf`.
   - **Категорически запрещено** коммитить в Git любые секреты: пароли `PostgreSQL`, ключи `MinIO` (`MINIO_ACCESS_KEY`, `MINIO_SECRET_KEY`), токен Telegram-бота (`TELEGRAM_BOT_TOKEN`), приватные ключи TLS и `SECRET_KEY` Django.
   - Все секреты передаются исключительно через переменные окружения (`.env`), которые исключены из Git через [.gitignore](../../.gitignore). В репозитории хранится только безопасный шаблон [.env.example](../../.env.example).
4. **Версионирование схемы базы данных**:
   - Схема БД версионируется исключительно средствами миграций **Django ORM** (`backend/apps/*/migrations/`).
   - Каждая миграция должна поддерживать возможность отката (`rollback`) и проверяться перед слиянием (`п. 3.3.1`).
   - Ручное изменение таблиц в БД в обход миграций запрещено.
5. **Хранение и версионирование документации**:
   - Проектная и техническая документация, спецификации и гайдлайны хранятся в директории `/docs` репозитория и маркируются номерами версий по схеме `vX.Y` (например, `v1.0`, `v1.1`).

## 2. Стратегия ветвления (Git Flow) и именование веток (п. 3.1, 3.2.1, 3.3.1)

В проекте применяется модель **Git Flow**:

### 2.1. Основные защищенные ветки
- **`main`** — защищенная ветка, содержащая только стабильный, протестированный код, готовый к развертыванию в `Production` (соответствует внешним вехам `M3–M6`). Прямые коммиты (`push`) в `main` запрещены.
- **`develop`** — основная ветка интеграции для текущей разработки. Все рабочие ветки вливаются в `develop` через Pull Request.

### 2.2. Рабочие и короткоживущие ветки
Для каждой задачи из бэклога, сценария использования, дефекта или запроса на изменение создается изолированная ветка от актуального состояния `develop`:

| Тип задачи | Формат имени ветки | Примеры |
|------------|--------------------|---------|
| Реализация сценария / функции (`US-01..US-08`, `FTR1..FTR7`) | `feature/US-XX-<краткое-описание>` или `feature/FTR-X-<описание>` | `feature/US-01-online-order`, `feature/US-02-auto-routing`, `feature/US-07-document-photo` |
| Исправление дефекта (бага) | `bugfix/<номер-дефекта>-<описание>` | `bugfix/BUG-012-invalid-pickup-code`, `bugfix/BUG-019-printer-timeout` |
| Одобренный запрос на изменение (RFC) | `feature/CR-XXX-<описание>` | `feature/CR-002-custom-banner-options` |
| Подготовка релиза к вехе | `release/vX.Y-<код-вехи>` | `release/v1.0-M4` |

### 2.3. Правила оформления коммитов
- Сообщения коммитов должны быть атомарными, понятными и содержать привязку к идентификатору сценария, требования или дефекта:
  - `feat(US-02): реализовать алгоритм автоподбора салона в RoutingService`
  - `feat(US-07): добавить кадрирование фото на документы 35x45 и 50x50`
  - `fix(U-C-03): отклонять файлы размером более 50 МБ в FileValidator`
  - `test(US-06): покрыть тестами выдачу заказа и исключения 2a, 5a, 7a`

## 3. Порядок внесения изменений и Pull Request (п. 3.1, 3.4.2)

Каждый шаг разработки (как человеком, так и агентом в режиме `/teamwork`) проходит через 5 обязательных этапов:

1. **Разработка и модульное тестирование**:
   - Разработчик выполняет задачу в изолированной ветке `feature/*` строго по гайдлайнам `docs/guidelines/00..07`.
   - Одновременно с кодом пишутся модульные и интеграционные тесты `PyTest` (`pytest-django`, `pytest-qt`).
2. **Создание Pull Request (PR)**:
   - Создается PR из рабочей ветки в ветку `develop`.
   - В описании PR указываются реализованные требования (`U-C-*`, `U-M-*`, `U-A-*`, `S-*`), сценарии (`US-01..US-08`) и способ их проверки.
3. **Автоматическая проверка CI (`GitHub Actions`)**:
   - При открытии/обновлении PR автоматически запускается пайплайн `.github/workflows/ci.yml`:
     - проверка стиля и статический анализ кода линтером (`ruff check .`);
     - проверка применения миграций (`python backend/manage.py makemigrations --check --dry-run`);
     - прогон полного набора тестов (`pytest`).
   - **«Зеленый» CI — обязательное условие слияния в `develop` и `main`**.
4. **Ревью кода (Code Review)**:
   - Каждый PR проверяется минимум одним другим участником команды / агентом-ревьюером.
   - Чек-лист ревью (п. 3.4.2):
     - соответствие архитектурным контрактам (`system_overview.puml`) и таблице переходов статусов;
     - покрытие позитивных и исключительных ветвей сценария (`1a..10a`) тестами `PyTest`;
     - соблюдение изоляции ролей (`CLIENT`, `MANAGER`, `ADMIN`, `S-SEC-03`) и отсутствие секретов в коде;
     - все пользовательские тексты и ошибки — на русском языке (`S-USE-01`).
5. **Слияние (Merge)**:
   - После успешного прохождения автотестов и одобрения ревьюера ветка сливается в `develop`, обновляется `CHANGELOG.md` и при необходимости актуализируется документация в `/docs`.

## 5. Управление изменениями (RFC) и матрица компромиссов (п. 1.1, 3.2)

1. **Матрица компромиссов проекта**:
   - **Ресурсы** (`1000 чел.-ч`) — **зафиксированы**;
   - **Время** (сдача до `25.12.2026`, вехи `M1–M6`) — **согласовывается / директивно ограничено**;
   - **Возможности** (`FTR1–FTR7`, `US-01..US-08`) — **принимаются (варьируемый параметр)**.
2. **Порядок работы с изменениями рамок (Request for Change, RFC)**:
   - Любое предложение, меняющее утвержденные требования, схему БД или состав функций первой очереди, регистрируется в GitHub Issues с меткой `change_request` и номером `CR-XXX` по форме п. 3.2.2.
   - Классифицируется на `Major` (затрагивает `FTR1–FTR7`, `US-01..US-08`, вехи `M1–M6`), `Medium` (логика модуля без сдвига сроков) или `Minor` (локальные правки UI/документации).
   - **Принцип эквивалентного обмена содержанием (Scope Trading)**: включение любой новой функции из списка исключенных (п. 3 Функциональной спецификации: автокадрирование лица, разделение заказа между несколькими салонами, отчеты/статистика, онлайн-оплата, курьер) допускается **только после решения Совета (CCB)** и при одновременном исключении функции сопоставимой трудоемкости `1:1`.
   - Самовольное расширение функциональности за рамки первой очереди (Gold Plating) запрещено.

## 6. Релизный цикл, окружения и развертывание (п. 3.3, раздел 6 Функциональной спецификации)

### 6.1. Окружения проекта
1. **`Dev` (Локальная среда разработки)**:
   - Запуск через виртуальное окружение Python (`venv`) + `pytest` либо локальный `docker compose up`.
   - Допускается использование `USE_MINIO=False` (локальное хранилище) и `YOUPHOTO_HARDWARE_MOCK=True` (эмуляция камеры и принтера).
2. **`Test / Staging` (Тестовый стенд)**:
   - Серверные компоненты в контейнерах `Docker Compose` на Linux (`PostgreSQL`, `MinIO`, `Django + Gunicorn`, `Background Worker`, `Nginx` с HTTPS/TLS).
   - Аппаратный стенд салона: ПК под ОС Windows 10/11 с `YouPhoto.exe`, подключенным по USB фотоаппаратом и принтером с драйверами Windows (`S-ENV-07`).
3. **`Production` (Продуктовая среда)**:
   - VPS-сервер на территории РФ (`152-ФЗ`, `S-ENV-03`), домен `.ru` с SSL/TLS-сертификатом (`S-SEC-01`), включенное ежесуточное резервное копирование БД (`S-REL-02`) и фоновая очистка фотографий старше 30 дней (`S-SEC-04`).

### 6.2. Контроль готовности по вехам (Milestones `M1–M6`, п. 1.2)
- **`M1` (Выработка концепции)** и **`M2` (Планирование)** — завершены (утверждены документы 1, 2, 3, UML-диаграммы и гайдлайны `00..08`).
- **`M3` (Готовность серверной части)**:
  - Реализованы и покрыты тестами `FTR1` (онлайн-оформление заказа), `FTR2` (очередь и автораспределение заказов между салонами) и `FTR4` (справочники филиалов, оборудования и услуг).
- **`M4` (Окончание фазы разработки)**:
  - Реализованы все функциональные блоки `FTR1–FTR7`, включая веб-портал клиента (`FTR3`), выдачу заказов по коду (`FTR5`), десктопное приложение сотрудника с импортом фото по USB (`FTR6`) и печатью через драйверы Windows (`FTR7`).
- **`M5` (Готовность к внедрению)**:
  - Заморозка кода (`code freeze`), пройдено приемочное и регрессионное тестирование по всем сценариям `US-01..US-08` и всем исключениям в них (`1a..10a`), проверены миграции и откат (`rollback`), собран автономный `YouPhoto.exe` через `PyInstaller`.
- **`M6` (Внедрение и демо работы)**:
  - Развертывание `Docker Compose`, первичное заполнение справочников салонов, оборудования, услуг и цен, smoke-тестирование и демонстрация полного цикла работы системы.

### 6.3. Шпаргалка команд для работы с репозиторием

```powershell
# 1. Установка зависимостей для разработки и тестирования
pip install -r requirements.txt -r requirements-desktop.txt

# 2. Применение миграций и проверка отсутствия незафиксированных изменений схемы БД
python backend/manage.py makemigrations --check --dry-run
python backend/manage.py migrate

# 3. Первичное заполнение справочников салонов, оборудования, услуг и тестовых ролей
python backend/manage.py seed_initial_data

# 4. Запуск линтера и полного набора автотестов PyTest
ruff check .
pytest

# 5. Запуск фоновой очистки фотографий старше 30 дней после завершения заказа (S-SEC-04)
python backend/manage.py purge_expired_photos

# 6. Сборка автономного исполняемого файла АРМ сотрудника под Windows (PyInstaller)
pyinstaller deploy/pyinstaller/YouPhoto.spec

# 7. Запуск полного серверного контура в контейнерах Docker
docker compose -f deploy/docker-compose.yml up --build -d
```
